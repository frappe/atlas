# Regional Runway cache

[Service VMs](service-vms.md)

Runway Cache Server is a Single record, like Cargo Server. It owns one privileged, termination-protected tenant-0 VM per region. Runway owns cache authorization, signing keys, storage, and the journal. Atlas owns the VM, release pin, setup, DNS, and operator route.

## Configure and provision

Save the release URL and its lowercase SHA256 on Runway Cache Server. Use an HTTPS URL without credentials. Set the Central HTTPS origin, issuer (`central`), JWKS URL, and Central Region name. Atlas Settings supplies the numeric region ID. Set different guest and operator ports, each between 1024 and 65535. Optional Central and storage CA fields hold public PEM certificates.

Select **Provision**, then select a System Virtual Machine Image and VM resources. An Active HTTP proxy is required. Atlas uses the normal VM path and SSH through the host. The service firewall admits the guest port from the region mesh (`/32`) and the operator port from tenant-0 mesh (`/64`). It does not expose SSH on the mesh. The existing Metal host SSH path remains available.

`internal-runway-cache-svc.<wildcard-domain>` is an AAAA record for the VM mesh address. Guests use this name and pin the Runway CA. They connect directly to the guest port, so the service sees their mesh source address.

## Release package contract

The pinned tar archive must contain `runway-cache/setup.sh` and the Runway release files. Atlas uses `install-service-package.sh` to download, verify SHA256, extract, and run setup. The VM stores the completed package hash in `/opt/atlas/runway-cache-package-hash`. The installer skips download and setup when this hash matches. A failed hash check does not run setup or change the installed hash.

Atlas writes `/etc/runway/cache-service.json`, `/etc/runway/central-ca.pem`, and `/etc/runway/storage-ca.pem` before installation. It supplies `RUNWAY_CONFIG`, `RUNWAY_STORAGE_CA_FILE`, and `RUNWAY_DOMAIN` to setup. Setup must install the Runway binary and `runway-cache-data.service` and `runway-cache-service.service`. It must create local TLS files under `/etc/runway/tls/`: `ca.pem`, `certificate.pem`, and `private-key.pem`. The certificate must cover `RUNWAY_DOMAIN` and the internal guest name. Setup must preserve existing keys and the journal on upgrades, and prepare the cache-data configuration and public signing key trust. These are Runway release responsibilities; Atlas does not generate or read these secrets.

The service configuration keys are `version`, `region_id`, `mesh_region_id`, `central_region_id`, `listen`, `operator_listen`, `central_issuer`, `central_jwks_url`, `central_url`, `central_ca_file`, `central_token_file`, `audience`, `certificate_file`, `private_key_file`, `signing_key_file`, `cache_data_ca_file`, and `archive_bytes`.

Atlas sets `audience` to the loopback cache-data origin `https://127.0.0.1:18445`. This listener is separate from the guest and operator listeners.

The signing key is generated by Runway at `/etc/runway/signing-key.pem`.

Central supplies its read credential through `/configure`; Atlas stores no credential. Team bucket endpoints and credentials come from Central at runtime. The storage CA path is passed to setup for cache-data's managed storage configuration.

## Operator route

Publish the current HTTP proxy package with `build-service-packages` and update existing proxy nodes before cache setup. The package includes the generated operator virtual host. Atlas sends the route and public CA through the normal proxy configuration delivery and digest checks, including newly created proxy nodes.

Central calls `https://runway-cache-svc.<wildcard-domain>/configure`. The regional wildcard certificate terminates public TLS at the proxy. The proxy accepts only POST on that exact path, then opens verified TLS to the VM mesh address and operator port. It verifies the service certificate against the public CA read from the VM and uses the service domain for SNI. Other paths return 404. The guest listener is never a proxy upstream. Runway validates Central's JWT and numeric region audience.

## Operate and recover

Setup moves through `Pending`, `Provisioning`, and `Active`. A failure sets `Failed` and records its phase. Pending or interrupted setup is queued each minute. Correct the cause and select **Re-provision** to retry on the same VM. Change the release URL and hash, save, then re-provision to upgrade in place.

Atlas writes configuration before installation. Runway setup restarts services only when installed files or configuration change. A matching package hash skips setup and leaves services running. To apply changed configuration inputs, rerun setup or change the release pin. The disk and journal stay in place.

**Archive** removes the operator route and internal DNS before terminating the VM. A replacement gets a fresh disk and service identity. Listener ports and Central Region name cannot change while a VM is attached. An outage makes Runway jobs fall back to GitHub's cache.

The controller verifies jobs with its GitHub App credential and records the result on the Central lease. The cache service holds no GitHub credential.
